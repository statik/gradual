01 Decision
Decision

Port the vip triage bot to GitLab as a webhook-triggered, three-job CI pipeline

A project webhook (issue + note + merge-request events) targets the project's own pipeline-trigger endpoint — zero external infrastructure. A gate job parses the webhook payload and sanitizes issue text; a read-only agent job runs pi against Claude on Amazon Bedrock inside a bubblewrap sandbox whose only network path is a Unix-socket bridge to a host-side SigV4-signing proxy; a separate write job validates a capped JSON intent file and executes labels, comments, and merge requests with a project access token. Trigger behavior is configurable; the default is opt-out (triage every new issue unless skip-triage).

# Design rule Choice Rationale
1 Event → pipeline Webhook → trigger endpoint GitLab cannot start pipelines from issue events natively; the project webhook can target its own /trigger/pipeline URL and the payload arrives as the $TRIGGER_PAYLOAD file variable. No receiver service to run.
2 Trigger mode Configurable, default opt-out One CI variable (TRIAGE_MODE) flips between triage-on-open (README behavior) and triage-on-label (current vip behavior).
3 Agent pi (earendil-works), opencode as alternate Clean headless mode (-p, deterministic exit codes, JSON event stream), first-class documented Bedrock env vars including a credential-free endpoint-override path. The sandbox supplies the security boundary pi lacks.
4 Model access Bedrock via GitLab OIDC → STS No static AWS keys. Credentials never enter the sandbox — a host-side signing proxy holds them.
5 Sandbox bubblewrap, no netns --unshare-all gives the agent zero network; the only egress is a bind-mounted Unix socket to the Bedrock proxy. just-bash rejected as primary (can't run real toolchains).
6 Writes Separate write job, capped intents Replicates gh-aw safe-outputs: the agent buffers intents to JSON; a job the agent never controls validates against allowlists/caps and executes with the bot token.
7 Runners Self-hosted required bubblewrap needs unprivileged user namespaces; GitLab.com shared runners can't be reconfigured (security_opt), and project access tokens are paid-only on GitLab.com.
The vip README is stale: it documents the original opt-out behavior, but the live workflow is opt-in via the needs-bot-triage label. This port supports both; the requested default is opt-out.
Trigger model

One webhook, one gate job, two modes

The project webhook (Issue events, Note events, Merge request events) targets https://gitlab.example.com/api/v4/projects/<id>/ref/main/trigger/pipeline?token=<trigger-token>. Every delivery creates a pipeline whose first job reads the full webhook JSON from the $TRIGGER_PAYLOAD file variable and decides — in seconds, on a tiny image — whether anything downstream should run. rules: can't see the payload (they evaluate before jobs run), so filtering is a cheap early-exit in the gate script, not a pipeline rule.

Event in payload TRIAGE_MODE=opt-out (default) TRIAGE_MODE=opt-in
Issue action: open Triage unless skip-triage label present No-op
Issue action: update with needs-bot-triage newly added (visible in changes.labels diff) Triage (manual re-run) Triage (the only entry point)
Note on issue matching @triage-bot retry Triage, only if the author is a project member with Maintainer+ role (checked via members API in the gate job)
MR action: merge, source branch bot-plan-issue-*, author is the bot user Run the implement flow (plan approved by human merge)
Anything else (issue edits, other labels, other notes) Gate exits 0; downstream jobs self-skip

The gate job also performs gh-aw-style input sanitization before any issue text reaches a prompt: strip ANSI/control characters, wrap @mentions in backticks, neutralize HTML/XML tags, redact non-HTTPS and non-allowlisted URLs, cap the body at 65,000 characters. The sanitized title/body are interpolated into a prompt template and passed downstream as an artifact — the agent never needs GitLab API access to read the issue.

In opt-out mode every issue update spawns a (cheap, no-op) pipeline. If the pipeline-list noise becomes a problem, the upgrade path is a ~50-line webhook receiver that pre-filters and calls the trigger API with clean variables — the rest of the design is unchanged.
Pipeline architecture

gh-aw's six jobs become three, same trust boundaries

The load-bearing property of gh-aw is that the agent never holds write credentials: it runs read-only and buffers write intents that a separate, trusted job validates and executes. The port keeps that split exactly; what collapses is GitHub-specific plumbing.

gh-aw job (GitHub) GitLab port Privileges Notes
pre_activation + activation — role gating, text sanitization, prompt assembly gate Read-only API token (members + issue lookups) Parses $TRIGGER_PAYLOAD, enforces mode + role gates, emits decision.env (dotenv artifact) + prompt.md
agent — Copilot CLI inside AWF firewall, read-only App token, MCP gateway agent Bedrock-invoke only, via signing proxy; no GitLab token at all pi inside bubblewrap; repo worktree bind-mounted; emits outputs/intents.json + outputs/changes.patch + JSONL event log as artifacts
detection — second LLM pass scanning outputs for injection/secrets Folded into write as deterministic checks (v1); optional LLM scan later — Secret-pattern scan (gitleaks) + path-denylist + size caps are deterministic and cheaper; an LLM threat pass can be added as a fourth job without changing interfaces
safe_outputs — validates JSONL, executes with write App token write Project access token (Developer, api scope), exposed only to this job via environment-scoped variable Caps: ≤1 comment, ≤3 labels from allowlist, ≤1 label removal, ≤1 MR, patch ≤1 MB / ≤100 files, path denylist enforced
conclusion — failure reporting Pipeline status + write failure comment — GitLab pipeline UI already provides the audit trail per run
Identity: project access token Creates a real bot user (project_<id>_bot_…) so comments and MRs are attributed and auditable — the GitLab analogue of vip's purpose-built GitHub App. Developer role + api scope; mandatory expiry, so calendar the rotation. CI_JOB_TOKEN is ruled out: it cannot create MRs, post notes, or change labels.
Concurrency & budget resource_group: triage-bot serializes agent runs (vip serializes per-issue; per-issue groups need the receiver upgrade). Timeouts mirror vip: 20 min triage, 30 min implement. pi's --mode json event log is kept as an artifact for token accounting.
Agent runtime

pi on Bedrock, with opencode as the documented fallback

Both candidates run headless and speak Bedrock. pi is recommended because its security posture matches this design: it has no built-in permission system and explicitly expects a container/sandbox boundary — which we provide — while offering the cleanest non-interactive contract and documented credential-free Bedrock routing. opencode's permission system is attractive but is application-level enforcement inside the same process; the sandbox makes that redundant.

Criterion pi (@earendil-works/pi-coding-agent) opencode (anomalyco/opencode)
Headless run pi -p "…" --mode json --no-session; exit 0/1 deterministic opencode run --format json; permission "ask" auto-rejects; exit semantics in flux (#10411)
Bedrock auth Documented: AWS chain, AWS_BEARER_TOKEN_BEDROCK, IRSA/OIDC, and AWS_ENDPOINT_URL_BEDROCK_RUNTIME + AWS_BEDROCK_SKIP_AUTH=1 (proxy holds creds) Documented, but open credential-chain bugs (#12984, #8559); bearer token most reliable
Tool restriction --tools read,grep,find,ls,bash,edit,write allow/deny lists per run Declarative permission config (allow/ask/deny, bash pattern rules)
GitLab prior art None — we build the harness (straightforward: it's a CLI) Official docs page + nagyv/gitlab-opencode CI component
Fit with this repo Recommended — this platform already builds on pi-agent-core Alternate — swap is contained to the agent job script

Models. vip uses Opus for triage and Sonnet for implementation; the port mirrors that. pi and opencode both resolve Bedrock models through the Converse API using cross-region inference-profile IDs (models.dev catalog). Verified-available profile IDs as of this memo: us.anthropic.claude-opus-4-5-20251101-v1:0 (triage) and us.anthropic.claude-sonnet-4-5-20250929-v1:0 (implement). Newer Claude models (Opus 4.8 at $5/$25 per MTok, Sonnet 4.6 at $3/$15) should be substituted as soon as they appear in your account's region catalog — confirm with aws bedrock list-inference-profiles and pin the IDs in CI variables, never in scripts. 

# Agent invocation inside the sandbox (draft)
export AWS_REGION=us-east-1
export AWS_ENDPOINT_URL_BEDROCK_RUNTIME=http://127.0.0.1:8888   # bridge to signing proxy
export AWS_BEDROCK_SKIP_AUTH=1                                  # proxy signs; no creds in sandbox

pi -p --mode json --no-session --no-context-files \
   --provider amazon-bedrock --model "$TRIAGE_MODEL" \
   --tools read,grep,find,ls,bash,edit,write \
   "$(cat /workspace/.prompt/prompt.md)" \
   > /workspace/outputs/events.jsonl
pi was rebranded from @mariozechner/pi* to @earendil-works/* (badlogic/pi-mono now redirects to earendil-works/pi). Pin the new scope and a specific version in the agent image.
Sandbox & egress

No network namespace at all — egress is a Unix socket you choose to mount

bubblewrap with --unshare-all leaves the agent with only a loopback interface. Instead of building IP-level firewall rules, the design exploits a simpler invariant: Unix sockets are filesystem objects and pass through bind mounts even with no network namespace. The host side runs a SigV4-signing reverse proxy for bedrock-runtime.<region>.amazonaws.com listening on a Unix socket; the sandbox gets exactly that socket and nothing else. The agent cannot reach GitLab, package registries, or attacker-controlled hosts because no route exists — allowlisting is "which sockets did we mount", not proxy ACL maintenance. 

# run-agent.sh (host side, draft)
# 1. OIDC → STS, host process only — never exported into the sandbox
eval "$(aws sts assume-role-with-web-identity \
  --role-arn "$AWS_ROLE_ARN" --role-session-name "triage-$CI_PIPELINE_ID" \
  --web-identity-token "$AWS_ID_TOKEN" --duration-seconds 1800 \
  --query 'Credentials' --output json | jq -r \
  '"export AWS_ACCESS_KEY_ID=\(.AccessKeyId) AWS_SECRET_ACCESS_KEY=\(.SecretAccessKey) AWS_SESSION_TOKEN=\(.SessionToken)"')"

# 2. signing proxy: unix socket → sigv4-sign → bedrock-runtime (host network)
mkdir -p /run/egress outputs
bedrock-sign-proxy --listen unix:/run/egress/bedrock.sock \
  --upstream "https://bedrock-runtime.${AWS_REGION}.amazonaws.com" &

# 3. throwaway worktree the agent may write to
git worktree add /tmp/work HEAD

# 4. sandbox: no net, ro toolchain, rw worktree, the one socket
bwrap --unshare-all --die-with-parent --new-session --clearenv \
  --ro-bind /usr /usr --symlink usr/lib /lib --symlink usr/lib64 /lib64 \
  --ro-bind /etc/ssl /etc/ssl --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --proc /proc --dev /dev --tmpfs /tmp \
  --bind /tmp/work /workspace --bind /run/egress /run/egress \
  --setenv HOME /tmp --setenv PATH /usr/bin:/usr/local/bin \
  --setenv AWS_REGION "$AWS_REGION" \
  --setenv TRIAGE_MODEL "$TRIAGE_MODEL" \
  -- /usr/local/bin/sandbox-entry.sh
# sandbox-entry.sh: ip link set lo up
#   socat TCP-LISTEN:8888,bind=127.0.0.1,fork UNIX-CONNECT:/run/egress/bedrock.sock &
#   …then the pi invocation from the previous section

# 5. after bwrap exits: harvest patch + intents
git -C /tmp/work diff --binary > outputs/changes.patch
cp /tmp/work/outputs/intents.json outputs/ 2>/dev/null || true
Why not just-bash vercel-labs/just-bash interprets bash + coreutils in-process with a virtual FS — superb isolation, but it cannot run real toolchains (git, linters, test suites), which the triage prompt requires for its "high-confidence fix" gate. Worth revisiting for a read-only classification-only tier.
Why not a proxy sidecar only The gh-aw approach (Squid + iptables DNAT, drop NET_ADMIN) works and is the portable fallback for docker-executor runners, but it is more moving parts and domain-ACL upkeep. Keep it as plan B where user namespaces are unavailable.
Runner requirement bwrap needs CLONE_NEWUSER; Docker's default seccomp profile blocks it. Self-hosted runner with security_opt = ["seccomp=unconfined", "apparmor=unconfined"] in config.toml, or shell-executor VMs. Not possible on GitLab.com shared runners.
This is the same architecture as Anthropic's sandbox-runtime (srt): filtering proxies outside, Unix-socket bridge inside, plus seccomp against new-socket creation. The signing proxy doubles as the credential boundary — gh-aw's "API proxy sidecar holding LLM keys", ported.
Conventions

Label state machine and the plan → implementation contract

Lifted from vip's workflow sources (not its stale README), with GitLab vocabulary. The human merge of a plan MR remains the approval gate for implementation.

Label Applied by Removed by Meaning
needs-bot-triage Maintainer (re-run in opt-out mode; sole entry point in opt-in mode) Bot, at run start (consume the request) Run triage now
skip-triage Humans Never by bot Hard opt-out; gate exits
triaged-by-bot Bot, on every successful path — Processed
plan-pending-review Bot (enhancement path) Implement flow, after plan MR merges Plan MR awaiting human merge
needs-human-triage Bot, when it can't classify or proceed — Escalation
implementing Implement flow — Implementation MR in flight
Plan → implement contract (three couplings) (1) Plans live at thoughts/shared/plans/<YYYY-MM-DD>-issue-<iid>-<slug>.md; (2) the plan file's first line is machine-readable: # Plan for issue #<iid>; (3) implementation triggers only on a merged MR whose source branch matches bot-plan-issue-* and whose author is the bot user — all three facts are present in the MR webhook payload, so no extra API round-trips to gate.
Scope guards (write job enforces) Denylist: .gitlab-ci.yml, .gitlab/**, triage-bot/**, CODEOWNERS, dependency manifests and lockfiles, CHANGELOG.md, .git/. New files only under selftests/, source tree, thoughts/shared/plans/. Mirrors vip: the bot can never modify CI machinery, its own prompts, or version pins — enforced outside the agent, in the write job, where the agent can't argue with it.

Output discipline mirrors vip exactly — exactly one outcome per run: bug → single fix MR; enhancement → plan MR + one issue comment; can't-proceed → one needs-human-triage comment; gate-exit → nothing.

Implementation draft

.gitlab-ci.yml skeleton

# Draft — names and images will vary by environment
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "trigger"

stages: [gate, agent, write]

variables:
  TRIAGE_MODE: "opt-out"            # "opt-out" | "opt-in"
  TRIAGE_LABEL: "needs-bot-triage"
  TRIAGE_MODEL: "us.anthropic.claude-opus-4-5-20251101-v1:0"
  IMPLEMENT_MODEL: "us.anthropic.claude-sonnet-4-5-20250929-v1:0"

gate:
  stage: gate
  image: alpine:3.21
  script:
    - apk add --no-cache jq curl
    - triage-bot/gate.sh            # parses $TRIGGER_PAYLOAD → decision.env, prompt.md
  artifacts:
    reports: { dotenv: decision.env }   # RUN_AGENT, FLOW, ISSUE_IID
    paths: [prompt.md]
    expire_in: 1 week

agent:
  stage: agent
  needs: [gate]
  tags: [self-hosted, userns]       # runner with unprivileged userns / relaxed seccomp
  image: $CI_REGISTRY_IMAGE/triage-agent@sha256:…   # pinned: pi, bwrap, socat, aws cli
  timeout: 20 minutes
  resource_group: triage-bot
  id_tokens:
    AWS_ID_TOKEN: { aud: "https://gitlab.example.com" }
  variables:
    AWS_ROLE_ARN: "arn:aws:iam::ACCOUNT:role/triage-bot-bedrock-invoke"
  script:
    - '[ "$RUN_AGENT" = "true" ] || { echo "gate: no-op"; exit 0; }'
    - triage-bot/run-agent.sh       # STS → signing proxy → bwrap → pi → harvest
  artifacts:
    paths: [outputs/]
    expire_in: 1 week

write:
  stage: write
  needs: [gate, agent]
  image: registry.gitlab.com/gitlab-org/cli:latest   # glab + jq
  environment: triage-bot-write     # GITLAB_BOT_TOKEN scoped to this environment
  script:
    - '[ "$RUN_AGENT" = "true" ] || exit 0'
    - triage-bot/apply-outputs.sh   # validate caps/denylist → labels/comment/branch/MR

apply-outputs.sh is the trust boundary: schema-check outputs/intents.json; enforce ≤1 comment (≤65k chars), ≤3 labels from the fixed allowlist, ≤1 removal (needs-bot-triage only), ≤1 MR; run gitleaks over the patch; reject any patch path on the denylist; then git apply onto a fresh bot-<flow>-issue-<iid> branch, push with GITLAB_BOT_TOKEN, and glab mr create. Labels and comments go through the issues/notes REST API.

The implement flow reuses the same three jobs with FLOW=implement: the gate extracts the issue IID from the merged plan MR's branch name and plan-file header, the agent gets the plan file contents in its prompt and a 30-minute timeout with IMPLEMENT_MODEL, and the write job opens the implementation MR (Closes #<iid>), swaps plan-pending-review → implementing.

Operations

Cost, rollout, rollback, observability

Deploy Ship triage-bot/ scripts + CI include in one MR; create trigger token, webhook, project access token, AWS OIDC provider + invoke-only IAM role; pin the agent image by digest. Start with TRIAGE_MODE=opt-in on a test project, flip to opt-out after a week of clean runs.
Rollback Disable the webhook (single switch — all entry points die), or set TRIAGE_MODE=opt-in to quiesce. Revoking the project access token kills writes even if pipelines still run.
Observe Pipeline list = audit log. Artifacts keep the sanitized prompt, pi's JSONL event stream (token usage per run), the raw patch, and the validated intents. Alert on write-job rejections — they indicate either agent drift or an attack.

Cost envelope. Triage on an Opus-class model at $5/$25 per MTok with a ~20-minute cap and prompt caching lands in the $0.50–$2 range per triaged issue; implementation runs on Sonnet ($3/$15) are similar despite longer transcripts. The dominant control is the timeout plus pi's bounded tool loop; add a hard ceiling later by metering the signing proxy (gh-aw's maxEffectiveTokens equivalent — it sees every request, so it can count tokens and cut off the socket).

Token hygiene. Trigger token and GITLAB_BOT_TOKEN are masked CI variables; the bot token is additionally environment-scoped so the agent job can never read it. Project access tokens expire (≤400 days) — calendar the rotation. AWS access is OIDC-federated with the role trust pinned to project_path + ref, so there is no long-lived cloud credential anywhere in the system.

Self-managed GitLab assumed. On GitLab.com you additionally need a paid tier for project access tokens (or a service account / dedicated user + PAT) and you cannot use shared runners for the agent job — bring your own runner fleet.
Sources and caveats

Evidence, confidence, and open questions

High confidence vip workflow sources (issue-triage.md, implement-plan.md, compiled lock files) read directly — opt-in trigger, label machine, safe-outputs caps, scope guards, App-token flow. GitLab trigger-API + $TRIGGER_PAYLOAD, CI_JOB_TOKEN limits, OIDC→AWS, and webhook label-diff behavior from docs.gitlab.com. pi flags/exit codes/Bedrock env vars verified from a clone of earendil-works/pi (commit 9ccfcd7). bwrap flags from bwrap(1); the unix-socket egress pattern from anthropic-experimental/sandbox-runtime.
Main caveats (1) bedrock-sign-proxy is the one component we write ourselves (~100 lines; or run mitmproxy/sigv4 equivalent) — pi's AWS_ENDPOINT_URL_BEDROCK_RUNTIME + AWS_BEDROCK_SKIP_AUTH=1 are documented, but test the pairing through a Unix-socket bridge early. (2) Whether GitLab.com shared runners permit CLONE_NEWUSER is unverified — design assumes self-hosted. (3) Bedrock model catalog varies by account/region; verify profile IDs before pinning. (4) opencode-on-Bedrock has open credential-chain issues if you choose the alternate agent. (5) Quick-actions-only notes returning 202 needs verification on your GitLab version.
